Part 2: Backend Architecture Deep Dive

1. Architectural Philosophy: The BLAST Protocol

The system is built on the BLAST protocol (Blueprint, Logic, Architecture, Scripts, Tools), which enforces a strict separation of concerns into three distinct layers. This ensures that high-level reasoning (AI) is decoupled from low-level execution (API calls).

The 3-Layer Model

  1. Layer 1: Directives (The “SOPs”)
    • Location: directives/
    • Format: Markdown files (e.g., MASTER_ORCHESTRATION.md).
    • Function: specific Standard Operating Procedures (SOPs) that define how a task should be approached. They act as the “system prompt” or “knowledge base” for the AI Orchestrator.
  2. Layer 2: Orchestration (The “Brain”)
    • Location: demo_pipeline.py (and future orchestrator.py).
    • Function: The decision-making engine. It takes a vague user request (e.g., “I’m a student”), selects the appropriate tools, and synthesizes the results.
    • Key Logic:
      • Persona Mapping: Maps “Student” -> High weight on Affordability/Commute, Low on Schools.
      • Flow Control: Decides to fetch data -> Score -> Rank -> Explain.
      • Intelligence: Calls Anthropic (Claude) to generate the final natural language justification.
  3. Layer 3: Execution (The “Hands”)
    • Location: tools/ and execution/.
    • Format: Pure, deterministic Python scripts.
    • Function: They simply do the work. They do not “think”; they fetch, parse, and return JSON.
    • Key Tools: fetch_tfl_commute.py, fetch_crime_data.py, fetch_air_quality.py.

2. The Data Ingestion Pipeline

The backend processes data through a linear pipeline: Candidate Selection -> Enrichment -> Normalization -> Scoring.

Step 1: Candidate Generation (fetch_scansan.py)

  • Input: Budget (£1000), Location Type (Rent).
  • Process:
    • Queries the ScanSan Property Intelligence API (simulated via cache for demo).
    • Filters 35+ London postcodes (E1, SW9, etc.) based on the affordability threshold.
  • Output: A list of area_codes (e.g., ['SW9', 'E2']).

Step 2: Multi-Source Enrichment

For each candidate area, the system systematically “enriches” the profile by calling specialized tools.

A. Commute Analysis (fetch_tfl_commute.py)

  • Source: TfL Unified API (Journey Endpoint).
  • Method: https://api.tfl.gov.uk/Journey/JourneyResults/{from}/to/{to}.
  • Logic:
    1. Checks .tmp/ cache for existing route data.
    2. If missing, calls TfL API with TFL_APP_KEY.
    3. Fallback Mechanism: If the API returns 429 (Rate Limit) or 401 (Auth Error), it seamlessly switches to an internal mock generator (calculating Haversine distance and estimating tube speed) to prevent a crash.
  • Data Points: Duration (mins), Transfers (count), Accessibility Score (0-100).

B. Environmental Health (fetch_air_quality.py)

  • Source: TfL AirQuality API.
  • Method: https://api.tfl.gov.uk/AirQuality.
  • Logic: Fetches the London-wide pollution forecast. Included for future “Wellness” persona scoring.

C. Safety & Crime (fetch_crime_data.py)

  • Source: UK Police Data API.
  • Method: data.police.uk/api/crimes-street/all-crime.
  • Logic:
    • Converts Area Code (E1) to Lat/Lon coordinates.
    • Fetches total crimes within a 1-mile radius for the last month.
    • Calculates a normalized safety_score (inverse of crime density).

Step 3: Caching Strategy (cache_manager.py)

  • Philosophy: “Write once, Read many”.
  • Implementation: JSON-based local file cache in .tmp/.
  • TTL: Cache validity is currently set to ~24 hours.
  • Benefit: Enables sub-second demo performance after the first run and reduces API costs/rate limits.

3. The Scoring Engine (score_and_rank.py)

Once data is gathered, it is normalized to a 0-100 scale and weighed against the User Persona.

Weighted Formula:

Final Score = (Affordability * Wa) + (Commute * Wc) + (Safety * Ws) + (Amenities * Wm)

Persona Configurations: * Student: Wa=0.4 (High), Wc=0.3 (High), Ws=0.1 (Low). * Parent: Ws=0.4 (High), Schools=0.3 (High), Affordability=0.2. * Developer: Investment=0.5 (High), Gentrification Potential=0.3.

4. The Explanation Layer

The final step addresses the “Black Box” problem by explaining why a recommendation was made.

  • Tool: generate_text_explanation.py.
  • Model: Anthropic Claude 3.5 Sonnet.
  • Prompting: The system constructs a structured prompt containing:
    1. The User Persona.
    2. The complete JSON data profile of the area.
    3. A specific instruction to “Balance the pros and cons” (e.g., “Good price, but bad safety”).
  • Output: A human-readable paragraph embedded in the final report.

5. Security & Configuration

  • Secrets Management: All API keys (TFL_APP_KEY, ANTHROPIC_API_KEY) are stored in .env, which is strictly ignored by git (.gitignore).
  • Local Execution: The entire backend runs locally on the user’s machine, ensuring no data leaks to external servers other than necessary API calls.
